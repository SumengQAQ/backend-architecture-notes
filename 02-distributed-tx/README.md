# 分布式事务

后端就是与现实世界的不可靠性做斗争的过程。把这一点体现得淋漓尽致的，非分布式事务莫属。

我听人不止一次提起过：

> "如果你搞定了分布式一致性，那么后端你就搞定了 80%"

不过分布式事务并不等同于分布式一致性。分布式事务只是一致性中的一个剪影，更全面、更复杂的那部分要参阅 DDIA（这块还没有深入）。

## 五种常见的分布式事务

- **2PC**：分"准备阶段"和"提交/回滚阶段"两步。只要有一个人无法准备或者超时，就全部回滚；反之全部提交。
- **3PC**：在 2PC 之前加一个自我检查阶段，此阶段不占用资源，所有人检查通过之后才进入下一阶段。在"提交/回滚阶段"，如果一个节点没收到协调者的消息导致超时，会自动提交。
- **TCC**：Try / Confirm / Cancel。先冻结资源，然后尝试 Confirm；Confirm 过程中出异常，就 Cancel。
- **Saga**：不纠结于如何预留资源、提交和回滚，转向"通过多步骤的补偿来实现最终一致性"。按有无中央协调者，又分编排和协调两种实现。
- **Outbox**：发件箱模式，结合消息队列实现最终一致性。

## 先从一致性说起

在深入分布式事务之前，先看看一致性的几种类型。从上到下，一致性逐渐减弱。

1. **线性一致性**：所有节点对所有的操作顺序都一致，而且要同时做出响应。理论最强，实际做不到。
2. **顺序一致性**：所有节点对所有的操作顺序都一致，但不要求同时响应。除非是银行那种系统，否则很少用。
3. **因果一致性**：再放宽一层，只在有因果需求的地方追求顺序，其余地方无所谓，也不要求同时响应。

   比如 A 发了一条帖子，B 看到之后在下面评论。那么其他用户必须先看到 A 的帖子，再看到 B 的评论。

4. **最终一致性**：要求最宽松。过程无所谓，只要最后是一致的就行。最常见。

## 分布式基础理论

- **CAP**：一致性、可用性、网络容错性，只能三选二。因为分布式网络不是 100% 稳定，所以实际只能在 CP 和 AP 之间选。
- **BASE**：基本可用、软状态、最终一致性。这是网络分区时选择了 A 要面对的代价：放弃 C，就会有软状态；因为有 P，所以只能是基本可用。
- **PACELC**：网络没有问题的时候，仍然要在 L（低延迟）和 C（强一致）之间取舍。以数据库主从复制为例：
  - **异步复制（PA/EL）**：用户改完头像点保存，主库写入成功就立刻返回"修改成功"，不等同步到从库，这是追求低延迟 L。但用户马上刷新页面读从库，看到的可能还是旧头像，牺牲了强一致。如果主从之间网络断了（P），从库依然能对外提供查询，可用性 A 还在。
  - **强同步复制（PC/EC）**：用户改完密码，主库必须等所有从库同步完成才返回成功。响应变慢，牺牲了低延迟，但能保证用户立刻读到最新状态，一致性 C 保住了。
