# DDD：战略设计与战术设计

就我个人目前的认知而言，DDD 是一套「如何了解并组织非功能性需求」的方法论。它关注业务，而不是技术如何实现——技术的部分很大程度由 PEAA 解决。

从业务大方向和具体实现两个角度看，DDD 分为两层：

| 层面     | 回答什么问题                                   |
| -------- | ---------------------------------------------- |
| 战略设计 | 大的模型如何划分为小模型，以及相互之间如何关联 |
| 战术设计 | 这些分出来的模块，逐个怎么击破                 |

## 战略设计

**限界上下文**属于解决方案空间，比如身份与访问上下文、退款上下文。

**子域**属于问题空间，进一步分为三类：

- 核心域：决定公司竞争力的核心业务
- 支撑域：辅助核心业务的定制化业务
- 通用域：权限、支付等通用功能

**统一语言**解决的是歧义问题。不同上下文里可能出现相同的用词，但含义不同。所以在开发之前，领域专家、架构师和各个工程师之间需要先确定某个术语指代的具体含义。

**上下文映射图**描述上下文与子域之间的关系。常见的关系有共享内核、遵奉者、客户方-供应方、开放主机服务、防腐层、分道扬镳。

## 战术设计

基础构件：

- 实体：拥有生命周期的实例，不同实例之间通过唯一的业务标识引用
- 值对象：可以被随时以相等属性完全替代的、无生命周期或生命周期从属于父实例的实例
- 聚合：在聚合边界内保证实体与值对象部分属性的一致性。不需要一致性的属性，不必每次都加载聚合的全部内容
- 聚合根：聚合的入口，通过某一个实例管控聚合中全部的实例

服务与事件：

- 领域服务：负责跨模型之间的协调
- 应用服务：负责编排领域服务和基础设施层
- 领域事件：描述已经发生的客观结果，通过消息队列或内存事件总线（订阅者模式）分发，实现解耦与最终一致性

持久化相关：

- 工作单元：全自动追踪脏对象、开启事务、提交与回滚、获取领域事件并发送至消息队列（通过发件箱模式）
- 事件溯源：一种只追加"数据如何变化"的持久化方式，通过从某个快照的时间点重放来得到当前状态。特点是不可以更改、可以溯源；缺点是事件版本升级困难，而且需要定期快照来避免全量重放
- 资源库模式：实现领域层定义的接口，对高层屏蔽低层的实现，封装数据库、缓存和其他第三方接口，向应用服务提供具备业务含义的操作。这样测试的时候方便 mock，也能屏蔽底层的变化

## 事件风暴

这是配套的、用来明确业务的方法。理念是把各个利益相关方组织在一起，通过各方视角来初始化与完善业务流程。

但迫于现实的压力，在大部分情境下事件风暴被一再推迟。

## 与六边形架构的关系

DDD 是一套架构的方法论，需要结合具体架构来实现。最常见的实现是六边形架构，也叫端口-适配器架构。

六边形架构里有"核心"和"外围适配器"的区别，天然映射到领域层和其余层级。这套架构通过接口实现控制反转，和 DDD 可以说天作之合。事实上大家提起 DDD，心中默认的实现大部分都是六边形架构。

## 什么时候不该用 DDD

架构没有银弹。以下三种情况，推进 DDD 需要再想一想：

- 其他人不了解 DDD，沟通成本过高
- 一次性脚本，确定不会有更多变化
- 简单业务规则，不涉及多个子域或上下文
