## TLA+

TLA+ 是一种**形式化规约语言**（formal specification language），由 Leslie Lamport 提出。它的用途是：**精确地描述一个系统的行为**，尤其是那些存在并发、消息传递、节点故障的系统。

需要先分清一个概念：**TLA+ 不是编程语言**。它写出来的东西不是能直接运行的程序，而是一份**数学模型**。这份模型规定了：

- 系统里有哪些**状态变量**；
- 每个变量可以取哪些值；
- 系统允许发生哪些**状态变化**。

写完模型之后，用配套的工具 **TLC**（TLA+ 的模型检查器）把这份模型**在所有可能的执行路径上跑一遍**，看看它是否违反你提出的性质（例如"总金额守恒""不会出现死锁"）。如果违反了，TLC 会给出**一条具体的反例**，也就是"在哪种执行顺序下会出问题"。

TLA+ 这个名字本身就是它的内容：**T**emporal **L**ogic of **A**ctions，动作的时序逻辑。整套语言由两部分组成——描述单个动作的普通逻辑，加上描述整体行为的时序逻辑。后文会逐步展开。

它最初由 Lamport 为并发和分布式算法设计，后来 AWS、微软等公司用它验证过 S3、DynamoDB 这类关键系统的一致性。它不是学术玩具。

还有一个常被提到的名字要区分一下：**PlusCal**。PlusCal 是建立在 TLA+ 之上的一种**算法语言**，写法更接近伪代码或编程语言——有 `while`、`if`、赋值语句这些。它写起来对程序员更友好，写完后会被**自动翻译成 TLA+**，再交给 TLC 检查。可以这样理解：**PlusCal 是"更好上手的前门"，TLA+ 是"它背后的数学语言"。**

## 为什么需要 TLA+

假设有一个"两个账户互相转账"的程序，逻辑是：

```
如果 A 的余额 >= 100：
    A.余额 -= 100
    B.余额 += 100
```

单线程下测试一百次都没问题。但如果两个转账同时发生，可能出现这种时序：

```
时刻 1   线程 1：读到 A 的余额 = 100（够转）
时刻 2   线程 2：读到 A 的余额 = 100（够转）
时刻 3   线程 1：A.余额 = 0，B.余额 += 100
时刻 4   线程 2：A.余额 = 0，B.余额 += 100
```

如果实现里"读"和"写"不是原子的，A 就可能被扣了两次而只加了一次，总额守恒被破坏。

这类问题叫**并发 bug**，特点是：

- 单线程、常见路径下测不出来；
- 只在某个特定的执行交叠下才出现；
- 这个交叠可能极罕见，线上可能几个月才触发一次。

测试之所以抓不住它，是因为并发下**可能的执行顺序是指数级增长的**。进程一多、步骤一长，组合数就爆炸，人工构造和随机测试都覆盖不全。

TLA+ 换了一种思路：**不写代码，先写模型，然后用工具把"所有可能的执行顺序"穷举一遍**。这正是模型检查器擅长的事——它不需要你想到那个 bug，它自己会去把每条路径都走一遍。

所以，TLA+ 的价值可以概括为：

> 在写代码之前，用数学把系统在"所有可能的情况下"检查一遍，提前找出那些测试覆盖不到的并发与分布式问题。
